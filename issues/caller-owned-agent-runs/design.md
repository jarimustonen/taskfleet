# Caller-owned worktree runs: Taskfleet–Omega Habitat contract (draft)

**Status:** proposal for human review; no CLI/API below is implemented by this document. Jari has additionally decided that caller-owned runs must never invoke workmux, including during creation or merge. [ADR 0010](https://github.com/jarimustonen/native-agent-host/blob/main/docs/decisions/adr-0010-taskfleet-worktree-agents.md) already settles the ownership question: Taskfleet owns run, node, Git worktree and settlement; Omega Habitat's per-user daemon launches and controls a separate Pi child in the verified checkout. This draft specifies the boundary, not a new ADR. The [issue](item.md) and [plan](plan.md) track implementation; the host's [manage-agent-worktrees issue](https://github.com/jarimustonen/native-agent-host/blob/main/issues/manage-agent-worktrees/item.md) owns the browser side.

## What a caller can rely on

One caller-owned spinoff run has one node (`n-0001`), an explicit `agent_owner: "caller"` and `lifecycle: "interactive"`. Ownership is a **persisted mode**, not inferred from missing PID, tmux, or kind. Interactive means no automatic terminalization on Pi exit; it is not a claim that Pi is connected or running. A caller-owned run begins `pending` (or `running` after an explicit activation event, if one is added), remains nonterminal through daemon restart, browser close and Pi stop, and ends only through Taskfleet settlement. Do not reuse normal worker retry/death or evidence-capture rules for a Pi Taskfleet never launched. Ordinary Taskfleet-launched runs retain their existing worker handshake, supervisor policy, telemetry and terminal outcomes. Existing terminal runs remain readable with their recorded schema; the new mode defaults only for newly created runs and must not retrospectively reinterpret older absent fields.

Proposed dedicated CLI entry point (name subject to CLI review) rather than treating `--interactive` or the test-only `--skip-materialize` as caller ownership. The input requires an absolute source checkout, explicit source branch, nonempty task/title and a caller-generated stable idempotency key scoped to that source and Unix user. Reject mismatched repeated inputs for a key (compare a durable normalized request fingerprint); never silently return a different task under the same key. No caller-provided final branch or worktree path is authoritative. Taskfleet returns an absolute canonical checkout and verifies that `git worktree` metadata, branch, source repo and node record agree; the daemon additionally opens it through its own safe path resolver and verifies the returned run/node/source/worktree match before launching Pi. Branch names and truncated run IDs are display-only. Admission and reservation must be per-user, with permissions confined to that user's Taskfleet state.

**PROPOSAL, not current command syntax or current output:**

```sh
taskfleet run create --agent-owner caller --kind spinoff \
  --source-repo /home/alice/src/project --source-branch main \
  --title 'Improve search' --task 'Improve search behavior' \
  --idempotency-key 2d50b6b8-0526-4b7b-90de-7e094daee65c --output json
```

```json
{
  "schema_version": 1,
  "data": {
    "run_id": "01m42przrf8jvhnkast59drwdc",
    "node_id": "n-0001",
    "agent_owner": "caller",
    "lifecycle": "interactive",
    "status": "pending",
    "source_repo": "/home/alice/src/project",
    "source_branch": "main",
    "branch": "wt/example-search",
    "worktree_path": "/home/alice/src/project-search",
    "checkout_verified": true,
    "supervisor": {"state": "confirmed"},
    "idempotent_replay": false
  }
}
```

The envelope, branch and path above illustrate *proposed* fields and values; final output must use Taskfleet's standard versioned JSON envelope and explicit error codes. A successful response means a published node with a verified checkout and confirmed independent supervision, **not** that Pi was started. A published run whose supervisor did not confirm boot is still recoverable: return an error with full run ID and actionable `run reattach` guidance; retry of the key re-reads the published run and checks/repairs supervision rather than claiming a running supervisor just because it replayed. `run show` should expose ownership, run/node/checkout and binding state on both live and terminal runs under the run's shared lock. A deleted checkout is reported as absent, never re-verified by a cached boolean.

The host must preserve the key across HTTP timeout/restart (or give the person the run ID and an inspection path), and distinguish Taskfleet's `status` from Pi control status. Pi launch failure is a recoverable caller-owned run, not a failed Taskfleet worker. A separate Pi command/receipt is not idempotent merely because run creation is; on uncertain Pi startup inspect ownership and native history before considering another launch. No automatic relaunch of an uncertain writer.

## The spawning agent's wait

A spawning agent may call `taskfleet run wait <full-run-id>` immediately after creation, expecting a wake when its child can no longer advance without intervention. Today `run/wait.rs` reads terminal `manifest.status`, a supervisor-stall hint, a **Taskfleet-worker** `worker.exited` clean-exit attention hint, or an escalated `node.awaiting_input`; it does not observe a daemon-owned Pi exit. Default timeout is six hours. The host's Pi child does not run through Taskfleet's `run-worker` shim, so recording a fake `worker.exited` would make the supervisor apply the wrong worker semantics. `--notify` fires on a terminal transition, not on Pi stop. The existing caller guidance in `crates/taskfleet/skills/{worktree-spinoff,taskfleet-run-overview,stint-start}/SKILL.template.md` says that a wait result can be nonterminal and must be distinguished from a landing.

**Proposed told signal:** after Taskfleet publishes the run, the daemon registers a generation-bound `caller.pi.started` fact with full run/node, verified checkout and Pi session UUID, then starts or reconciles control of that exact Pi; after it has reaped that Pi, it records `caller.pi.exited` with the same generation/session and exit reason. If launch fails *before* a Pi child exists, record `caller.pi.launch_failed` instead. The command syntax is undecided; these are proposed event names, not permission for arbitrary `taskfleet event create` callers to assert a Pi exit. `started` records a launch attempt/ownership generation, not proof of continuing liveness; `launch_failed` resolves a generation that never acquired a Pi writer. Taskfleet must authenticate the same-UID caller/verified run and reject wrong generations, mismatched session IDs, and contradictory or replayed transitions. A repeated identical exit is idempotent. A new Pi generation after a stop requires the writer-fence/ownership protocol and makes the prior stop a historical fact, not the current state. A daemon that dies before recording an exit has **not** told Taskfleet that Pi stopped; the inherited Pi owner lock and history may help reconciliation, but neither a missing daemon nor a silent Pi process is an exit event. At restart, the daemon may report `caller.pi.control_uncertain` for that generation if it cannot re-establish control or prove exit. This is an attention signal, **not** proof that the writer is quiescent. Registration timing and the crash window between launching Pi and persisting `started` require the same no-duplicate reconciliation as session binding; do not promise an atomic cross-process launch.

**Proposed `run wait` predicate:** for a caller-owned, nonterminal run, settle on a durable current-generation `caller.pi.exited`, `caller.pi.launch_failed`, or `caller.pi.control_uncertain` (or on a post-grace explicit human-input request or confirmed supervisor stall). Terminal `done | failed | cancelled` takes precedence; for an unmerged run with both Pi exit and dead supervisor, surface Pi-stop attention *and* supervisor recovery context rather than masking the told exit as a generic stall. `caller.pi.started` alone never settles; an unstarted run without failure or explicit attention, and a healthy controllable Pi with no stop, intentionally remain pending. A daemon crash **without a recorded uncertainty fact** also remains pending: the waiter must use a bounded timeout, not infer exit from silence. These nonterminal wait outcomes do not append a terminal report or change `manifest.status`. `run wait` must latch the generation and reason from the settling poll, then read manifest/node together under `LOCK_SH` for the response; if a newer generation or terminal event races the response, expose both the latched reason and current state rather than presenting an obsolete stop as a currently stopped Pi. On `--any`, a caller must inspect the matching element of `data.runs[]`; other elements may still be pending.

**PROPOSED JSON, not an existing `run wait` shape:**

```json
{
  "schema_version": 1,
  "data": {
    "outcome": "condition-met",
    "condition": "all",
    "runs": [{
      "run_id": "01m42przrf8jvhnkast59drwdc",
      "status": "running",
      "merged": false,
      "landed": false,
      "caller_agent": {
        "state": "stopped-unmerged",
        "generation": 1,
        "pi_session_id": "3b875344-b416-4644-a4c2-1df6e7655ffd",
        "reason": "pi-exited",
        "settled_generation": 1,
        "current_generation": 1,
        "control": "stopped"
      }
    }]
  }
}
```

Exit `0` means `condition-met` **without** `--fail-on-error`, even for `stopped-unmerged`; with `--fail-on-error`, exit `3` for this attention outcome, launch failure, uncertain control, cancellation, or stall, while still emitting the normal data envelope. A confirmed merge returns terminal `status: "done"`, `merged: true` and the existing `landed`/`landed_method` verification; exit `0` with `--fail-on-error` only when the settled set actually meets the existing success grading, not merely because Pi stopped. Explicit cancel returns `status: "cancelled"` and exit `3` under `--fail-on-error`; `landed` is still the independent Git verification result, not forced false by cancellation. Neither `cancelled` nor even an incidental `landed: true` means this run recorded an explicit merge. A recorded `control_uncertain` settles with `caller_agent.state: "control-unknown"` and `control: "unknown"`; it must not be labelled `stopped-unmerged`, and `landed` remains an independent Git observation rather than evidence of Pi control. A timeout (exit `2`, `data.outcome: "timed-out"` even with `--fail-on-error`) carries `status` and last **told** generation/state plus `caller_agent.control: "unknown"` when control cannot be proved; lack of new events is never reported as an exit. Usage/unknown run remains exit `1` with an error envelope. The proposal preserves `data.runs[]`, `data.outcome`, and the existing distinction between settled and landed; existing worker waiters retain their old predicates and fields.

The spawning agent should use a bounded `run wait --timeout 60s --fail-on-error --output json` through a background-command facility and branch on `data.outcome`, `data.runs[].status`, `caller_agent.state` and `landed`, **not** exit code alone. On `stopped-unmerged`, it can inspect the branch/report and arrange explicit merge, salvage, or a human decision; it cannot declare the work done. On `control-unknown` or a timeout, inspect `run show` and the host's native ownership/history, request reconciliation or user intervention and preserve the checkout; only re-wait if someone still owns follow-up. A stopped Pi is not writer-quiescence proof for merge/discard; the settlement fence below remains necessary. If a Pi is intentionally left open for hours, a timeout is an honest pending check-in, not a success or a reason to tear down the run.

## Creation, replay and supervision

Reserve `(source_repo, source_branch, key)` before external effects; persist full run ID, normalized request fingerprint, materializer lease and a resource ledger sufficient to identify the branch/worktree *before* invoking a creator. Stage events/projections privately; publish atomically only after `node.created` records the actual verified checkout. Key replay must return the same run/node/checkout once published, including after a lost response. Serialize concurrent retries. If creator is live, wait boundedly or return `creation_in_progress` with run ID. If dead, reconcile the staged ledger against exact Git identities: adopt a verifiably intact checkout into the **same reserved run**, or preserve and return `creation_uncertain` with run ID, paths and manual recovery instructions. Do not replace the reservation with a new run while a possibly work-bearing checkout exists. Only after *proving* no owned external resources or work remain may a failed attempt be rolled back and retried; record that proof and cleanup obligation durably. Unknown Git/tmux state fails closed. This is a change from the current stale-creator reclaim/rollback path, which can assign a replacement run ID.

Caller-owned provisioning uses a Taskfleet-owned `git worktree add` path, with source/branch verification, durable receipts and conservative rollback. It does not invoke workmux, make a tmux window or launch a dummy worker. The current `run/spawn.rs` passes a generated launcher to workmux and requires a live worker PID handshake; that path remains for ordinary workers but cannot serve caller-owned creation. Placement is an explicit Taskfleet–host path contract rather than an interpretation of workmux configuration.

The supervisor must not be a descendant **in the host daemon's service cgroup**. Double-fork/`setsid` in `run/supervisor_spawn.rs` solves terminal/session ownership and zombie handling, not systemd cgroup membership; the host daemon unit uses `KillMode=mixed`. Recommend launching the *Taskfleet create/reattach CLI* in a per-user transient systemd unit/scope outside the daemon service cgroup, with an explicit same-UID unit ownership and readiness check before success is reported. Merely moving the supervisor after daemon-launched creation risks a kill window. Exact service manager invocation, privileges, naming and restart policy require a host deployment decision and disposable service test. If the independent launcher is unavailable, fail creation before external effects, or retain a published recoverable run with an explicit supervision error; never report a durable supervised success. `run reattach` must use the same independent launch path for caller-owned runs, including after merge/report failure; reconciliation inspects persisted events and resumes without synthesizing worker-death facts.

| Crash boundary | Durable evidence | Safe retry/recovery |
|---|---|---|
| Before reservation | None | Create once with same key. |
| After reservation, before external effects | Key, run ID, fingerprint, creator lease | Wait for live owner; after proven death resume same run or release only with proof of no resources. |
| During worktree creation / before receipt | Key + planned resource ledger; Git may hold branch/tree | Reconcile exact Git identities; adopt same run only if verifiable; otherwise preserve and report uncertainty. Never blindly force-remove. |
| After checkout receipt, before `node.created` | Staged ledger + verified Git identity | Validate again and append node under lock, or preserve for manual resolution. |
| After `node.created`, before publication | Staged event log/projections and key | Replay above `applied_seq`; publish same complete run if checkout still verified; no second checkout. |
| After publication, before supervisor confirms | Published run/node/key; independent supervisor may or may not be live | Return/replay same identity, inspect recorded PID identity, reattach if dead; no duplicate supervisor. |
| After success, before HTTP response / Pi launch | Published run and confirmed supervision | Replay identities; host opens and verifies checkout, then starts Pi exactly once if ownership is certain. |
| Pi started, before binding reply | Pi history/owner lock may exist; Taskfleet binding or `caller.pi.started` may not | Look up exact session/lock; reconcile same generation if proven; otherwise show uncertainty, no second Pi. |
| Pi exits, before daemon records exit | Last told start/binding, native Pi history and owner lock; no exit fact | Wait remains pending until verified reconciliation records exit/uncertainty; a bounded timeout wakes the caller without claiming completion. |
| Daemon killed before it can reconcile | Last told generation; writer control unknown, supervisor remains independent | On daemon restart record control uncertainty if control/exit cannot be proved; timeout in the interim, never synthesize clean worker exit. |
| Merge Git ref moved, before report | `merge.started` with immutable OIDs | Existing `run merge` recovery verifies OIDs; do not guess from branch ancestry. |
| Terminal event, before evidence/cleanup | Event log and node projection | Supervisor retry after writer fence; preserve resources if fence or history retention cannot be proved. |

All event writes/replay use `LockedRun` and the `applied_seq` watermark; multi-file reads take a shared lock. A creation retry cannot rely solely on a directory, PID liveness, or a branch fragment. Errors must include the canonical run ID when one has been reserved and distinguish retryable contention from manual intervention. An unkeyed caller-owned create should be rejected rather than silently forgoing this recovery contract.

## Pi binding, retention and settlement

The daemon starts Pi as the user's child in the reopened verified checkout, chooses the Pi UUID before launch and uses its existing per-session ownership lock. Propose `taskfleet run session bind <full-run-id> --node n-0001 --pi-session-id <uuid> --session-path <absolute-path> --checkout <absolute-path> --output json` (PROPOSAL). Taskfleet verifies same UID, run/node ownership, recorded checkout, Pi session header ID and original `cwd`, and a bounded safe path under the user's Pi session store; register with an append/apply event under the run lock. Repeating the identical binding succeeds without duplicating an event; replacing it requires an explicit, audited transition after proving the previous writer ended. A lost bind response is recovered by reading the node binding. Bind state is immutable history after teardown. Do not equate the host's Pi `session_id` with Taskfleet's normal-worker `evidence` field: those sessions are created and archived by Taskfleet's own launcher. Before teardown, guarantee a stable read path for history even when the original `cwd` has disappeared. **Recommendation:** keep Pi's native history as source of truth and let the host read it via the bound ID/path with the same bounded, no-symlink checks it already uses, independent of workspace discovery. If retention of a native path cannot be guaranteed by Pi/host lifecycle, require a verified archive before cleanup instead; do not claim a Taskfleet archive already exists for caller-owned Pi. The host currently attaches history to a discovered workspace by exact header `cwd`, so binding alone does not make it visible in today's browser.

Settlement remains explicit through Taskfleet's `run merge`, `run cancel`, `run discard --force --reason`, and (when appropriate) `run salvage`; browser exposure of these actions is the host's choice. Today `run merge` embeds `crates/taskfleet/scripts/merge.sh`, whose backend calls `workmux merge`. Refactor the merge driver into Rust before enabling caller-owned settlement: Taskfleet owns target-worktree resolution, serialization, cleanliness checks, the recorded merge transaction and OID compare-and-swap, report submission, recovery and error mapping. It may invoke Git subprocesses for rebase/ref operations; moving orchestration into Rust does not mean reimplementing Git. Preserve the existing crash and concurrent-merge guarantees, including the driver-death window, rather than substituting an unguarded `git merge`. Use a Git-only backend for caller-owned runs; ordinary worker creation may keep workmux, but no caller-owned command (including retry, reattach or cleanup) may invoke it. Inventory any workmux-merge-specific behavior relied on by ordinary runs before changing their backend; migrate ordinary merges to the same Rust-owned Git driver after parity tests and remove the embedded script rather than maintaining two merge engines. Merge is OID-pinned and the only successful integration truth; only a confirmed explicit merge authorizes force teardown. Cancel does not mean discard: retained unmerged commits, dirty/untracked work and uncertain state survive. Discard is a distinct audited operator authorization and never changes the terminal outcome. A still-running Pi can write during Git merge or cleanup; Taskfleet's own worker PID and the daemon's in-memory status are insufficient proof of quiescence. **Open cross-component protocol:** recommend a per-run/node writer lease acquired before Pi launch and inherited by Pi, plus a settlement fence that prevents new launches, asks the daemon to stop/close RPC, waits for the inherited lease to release, and verifies the exact checkout immediately before proceeding. The fence must survive daemon restart, avoid unlink/replacement of the lock inode, and define recovery if the daemon dies while Pi survives. Taskfleet owns the final permission to merge/remove; if lease or control state is unavailable it refuses destructive progress with an actionable `writer_uncertain` result. Git merge should not begin until the fence is held, and it should remain held through supervisor teardown (including reattach). A cancel may record terminal intent without deleting work, but must not silently close a live writer's checkout; retain until fenced. Whether human terminal agents outside the daemon can write into this checkout requires an explicit policy, not a promise that a same-UID advisory lock can police arbitrary writers.

For placement, Taskfleet returns actual verified absolute paths, never a path guessed from branch naming. The host currently discovers immediate `~/src` children and refuses paths outside its safe resolver. Agree a collision-safe Git worktree destination with the host, then test it with the daemon's `openat2` restrictions (including its mount policy). If a safe immediate child cannot be provided, extend host discovery for explicitly Taskfleet-verified nested paths with equivalent containment, or make creation unavailable for that workspace. Do not relocate or adopt manual worktrees. The host's [integration design](https://github.com/jarimustonen/native-agent-host/blob/main/issues/decide-taskfleet-browser-integration/design.md) leaves placement and browser settlement UI to implementation.

## Disposable acceptance tests

- Use two temporary Unix homes, separate `TASKFLEET_HOME`s and Git repos; never touch installed Taskfleet, personal tmux, Pi history or workmux config. Create a caller-owned run without Pi; assert exact run/node/branch/checkout, no worker PID or window requirement, confirmed supervisor, and that daemon/Pi absence does not terminalize it. Re-run against a normal Taskfleet worker and a pre-existing terminal run to prove isolation.
- Inject crashes at each matrix row (including a materializer that exits after making a dirty tree), concurrent same-key requests and mismatched payloads. Assert stable identity or explicit uncertainty, no duplicate worktree, no force rollback of uncertain work, projections replay correctly, and supervision reattach after publication.
- In a disposable systemd user/service fixture with `KillMode=mixed`, stop/restart daemon after creation and while Pi is running. Verify the independent supervisor survives, Pi loss does not *terminalize* the run, and restarting the daemon cannot issue an unproven second Pi launch.
- With a disposable spawning-agent waiter (`--fail-on-error --output json`), exercise started Pi remaining open (bounded timeout 2), told exit without merge (nonterminal `stopped-unmerged`, condition met, exit 3), and a lost exit event during daemon crash (no invented stop; timeout 2, then told `control_uncertain` wakes with exit 3 after restart). Repeat with `--any` and two runs: only the stopped/uncertain run is settled. Check `--progress` and race of stop followed by a new generation so the response cannot misidentify the current writer.
- Explicit merge after Pi exit must wake `run wait` as `done`/merged/landed (exit 0 under `--fail-on-error` when verified). Attempt cancel during a live/unknown Pi writer: where cleanup could affect that writer, refuse or defer until the fence is established; after authorized cancel, wait wakes as `cancelled` (exit 3 under `--fail-on-error`) without deleting unmerged work or treating the cancel event as proof of writer quiescence. Check an ordinary Taskfleet-launched worker and a historic terminal run retain their existing wait behavior.
- Use disposable Pi JSONL and ownership locks: bind and repeat, reject foreign/corrupt header and mismatched run/node/checkout, read history after successful merge removes checkout, and preserve work if history cannot be retained. Exercise writer-active/daemon-dead/stale-lock cases against merge, cancel and discard; explicit merge transaction recovery must still use immutable OIDs.
- Test discoverability at `~/src` with the chosen Git worktree placement, plus nested, manual, symlink and outside-home paths; outside/unverified paths remain inspection-only. Assert no workmux executable is called by caller-owned create, replay, merge, cancel, discard, reattach or supervisor cleanup under a stripped PATH; separately verify the ordinary worker path still behaves as before.
- Test the Rust merge driver against the existing merge fixtures: concurrent merges, dirty source/target, conflicts, source-OID movement, driver death, report crash recovery and cleanup ownership. Remove the embedded shell backend only after both ordinary and caller-owned merge semantics pass. Run the Taskfleet release gate before merging implementation; these design-only tests are proposals, not results.
