# Caller-owned writer fence (implementation contract proposal)

**Scope.** This is the Taskfleet ↔ Omega Habitat settlement protocol for one caller-owned spinoff (`n-0001`); it does not change the approved ownership split in ADR 0010. Nothing here is implemented yet. In particular, today's `require_writer_fence` deliberately refuses merge, cancel, salvage and discard for caller-owned runs. `caller.pi.lifecycle` and `caller.pi.session_bound` are useful observations, **not** writer credentials. Caller-owned create/retry/merge/teardown must never invoke workmux. This document replaces the open settlement-fence sketch in [design.md](design.md), not its creation, placement or history work.

## Two locks, one durable intent

Use a **dedicated persistent per-run lock**, not the host's existing `piOwnership` lock. The latter is keyed by Pi session UUID under the daemon's ephemeral service runtime, and is recreated after reboot; a run can have several Pi generations/sessions. It excludes only cooperating writers of one native session, and Taskfleet cannot reliably find the same inode after a runtime restart. Keep that lock for native session ownership, but do not use it as Taskfleet's destructive-work fence.

On reservation, **Taskfleet** creates `<TASKFLEET_HOME>/runs/<full-id>/writer.lock` (initially under `.creating/<id>/`, atomically published with the run), and a separate `launch-gate.lock` there. Both are empty, permanent, regular 0600 files in 0700 same-UID directories on a local filesystem supporting Linux `flock`; include their `(st_dev, st_ino)` in the staged ledger and durable run creation record before publishing. Fsync files and parent directories, including after staging rename. Never unlink or replace either inode, including at teardown: retain the small run state as long as a bound session/history can be referenced. All participants open relative to a verified run-directory FD with `openat(..., O_NOFOLLOW|O_CLOEXEC)`, `fstat` UID=current mapped user, regular type, mode=0600, `st_nlink=1`, and match recorded device/inode; re-open/re-stat the pathname and its trusted parent before and after locking and before irreversible action. Reject symlinks, hard links, wrong owner/mode, inode change, unknown/missing metadata or unsupported flock filesystem as `writer_fence_unavailable`. Never create/repair missing locks on replay, reattach or settlement. Existing runs predating the ledger stay settlement-disabled until an explicitly reviewed enrollment proves no active writer; do not manufacture a replacement lock on demand. `TASKFLEET_HOME` itself must resolve to the verified same-user private state root; home/path changes are not silent migrations.

`writer.lock` is a **shared (`LOCK_SH`) lifetime lease** for each host Pi generation. The daemon obtains a fresh open-file description and nonblocking shared flock, verifies inode and run/node/checkout identity, and passes that FD through `exec.Cmd.ExtraFiles` into Pi **before** `Start`. Pi holds it through its entire lifetime, including daemon death; the daemon keeps its own reference until it has reaped that exact child, then closes it. Close-on-exec is cleared only for that explicit Pi child FD; avoid propagating it to tools unless those tools can still write to the checkout, in which case inheritance is deliberate and settlement waits for them too. The host's existing `Pdeathsig=SIGKILL` kills the direct Pi when the daemon dies but does not prove grandchildren or detached tools exited. Before releasing the daemon's FD, stop accepting RPC and account for direct child exit; inherited FDs from any participating descendants keep the lock held. Keep `piOwnership` for per-session exclusion in addition to, not instead of, this per-run lease. A daemon unable to pass/verify the FD must refuse launch, not launch unfenced Pi.

`launch-gate.lock` is a short-lived `LOCK_EX` mutex, **not** the lifetime lease. Every fresh launch and continuation for a bound caller-owned run must pass it. While holding the gate, acquire the run's exclusive `.lock`, replay unapplied events, verify the run/node/recorded checkout and that `settlement_intent` is absent and status is live; reserve the next generation with exact session identity in an append-and-apply event (`LockedRun`, fsynced event then projections). Still under the gate, open and take `LOCK_SH` on `writer.lock` (nonblocking), verify its inode again, then release the run lock, launch Pi with that inherited FD, and release the gate **only after Start has returned or been proven to fail**. Persist `caller.pi.started`/binding with their generation; a reserved generation with a lost launch response is *uncertain*, not an invitation to start another child. On restart first reconcile exact child ownership/lease/native history or record uncertainty and require intervention. An old session's continuation takes the same gate even if its native session lock is free. Browser requests and any alternate host entry point must use this path; refusal to acquire the gate is retryable, refusal due to intent is permanent for this run.

Taskfleet settlement first acquires the gate `LOCK_EX`, then the run `.lock` `LOCK_EX`, and appends an idempotent `caller.settlement_intent` event for `merge | cancel | discard` (full run/node ID, operation key, actor, reason as applicable, recorded lock dev/inode and generation). The event's durable presence, not an RPC stop receipt, closes admission: a launch holding the gate finishes acquiring its shared lease *before* intent can be recorded; a launch arriving afterward sees intent and cannot start. **No transient marker file or unchecked projection read may grant permission.** Drop run lock, then gate. Ask the daemon to cease RPC/stop its Pi (best effort), take `writer.lock` `LOCK_EX` with a bounded wait, and verify the *same inode* and checkout/Git identities again. A lock timeout means `writer_active` or `writer_uncertain`, preserving the intent and all work; it never means Pi has stopped. On uncertain lost response, read the intent under the run lock and resume the same operation key; different operations conflict. An intent is sticky even on merge conflict/timeout: explicitly audited `run settlement abandon` may clear it only before Git mutation/terminalization, while holding gate and exclusive lease and verifying that no pending transaction/cleanup exists. Abandonment is not an automatic retry or launch permission after an error.

**Lock order:** gate → run lock → shared lease for admission; gate → run lock (persist intent), release both → exclusive lease → Git merge lock → short run locks for transaction/report for settlement. Never block on the gate, lease or Git lock while holding the run lock. Supervisor and reattach acquire the exclusive lease *before* run lock for cleanup/recovery; they never acquire the gate while holding either. Dry-run uses shared-locked observations but cannot claim quiescence. Existing run/event APIs keep their exclusive `LockedRun` append witness, `applied_seq` replay and shared lock for multi-file reads. Git subprocesses are outside run-lock critical sections. Recheck intent and recorded inode under the run lock immediately before any destructive step; a path revalidation error preserves resources.

## Operation phases and outputs (new CLI proposals, not current syntax)

1. Host: `taskfleet run writer launch-reserve <id> --node n-0001 --generation 1 --pi-session-id <uuid> --checkout <absolute> --output json` is a *protocol operation*, not a standalone admission token: it must run under the daemon-held gate and pair with the inherited shared lease and exact launch check above. Prefer an FD-aware Taskfleet library/helper over an independent CLI whose exit would release the gate before `Start`. Taskfleet returns recorded run/checkout and generation; the daemon verifies exact repo, branch, canonical checkout, native history identity and same UID before spawning. A bare same-UID CLI assertion is never attestation of Pi ownership.
2. Operator: `taskfleet run settle <id> --operation merge --key <stable-uuid> [--report-file ...] --output json` (or compatible `run merge` flags). Phase `intent-recorded` may return `writer_active`, with no Git changes; phase `quiesced` holds the exclusive lease for Git transaction and report. Preserve the existing merge serialization, source-OID CAS and immutable-OID recovery; the Git-only driver may not call workmux. Successful `run merge` appends the `via: explicit-merge` report and confirms/reattaches an independent supervisor. **Never return cleanup complete merely because the report landed.** On timeout waiting for cleanup, return `merged: true, cleanup: pending` with an exact reattach instruction.
3. Supervisor after report or restart: re-open the recorded inode, acquire exclusive lease (bounded/retry), read intent and immutable merge transaction under the run lock, verify retained Pi history is readable via its bound native ID/path (or a verified archive) and checkout/Git identities, then perform Git-only cleanup and record cleanup completion while holding the lease. Crash after Git ref move but before report: recovery must acquire exclusive lease and resolve only the recorded OIDs; until resolution it preserves the tree. An already recorded merge intent is sufficient to fence future launches even if the merge process dies and the lease is released. Reattach repeats the same check. Thus **logical quiescence lasts through cleanup** without depending on one process keeping `LOCK_EX` continuously: there is no interval for a *cooperating* new generation between the merger releasing its FD and the supervisor reacquiring it. Do not reopen launches after teardown.
4. Cancel while writer active: record `cancel` intent, stop accepting RPC and request shutdown, but **defer terminal cancel/cleanup** until exclusive lease can be acquired; return `intent-recorded, writer_active` rather than `cancelled`. With lease held, append cancellation under the run lock; preserve branch and any dirty/unmerged checkout under existing non-merge rules. Do not equate cancellation with deletion or with permission for later Pi continuation. If the runtime is unavailable, this is still safely fenceable via local state but remains pending if a lease cannot be obtained.
5. `run discard --force --reason ...` is allowed only on failed/cancelled terminal runs with retained work. With the sticky intent and exclusive lease held, revalidate authorization, supervisor ownership, Git identities and history retention before audited `cleanup.discard_authorized`, then remove worktree/branch through Git; `--force` authorizes loss of work, **not** bypass of a writer lock, missing inode or unreadable history. `run salvage` uses the same merge path and intent, never the normal worker PID fence. Keep existing run/node/status rules and source relative work-preservation checks.

Example success (proposed versioned Taskfleet envelope):

```json
{"schema_version":1,"data":{"run_id":"01m42przrf8jvhnkast59drwdc","node_id":"n-0001","operation":"merge","phase":"reported","intent_seq":8,"writer_fence":{"state":"quiesced","lock_dev":2049,"lock_ino":53100},"merged":true,"cleanup":"pending","recovery_command":"taskfleet run reattach 01m42przrf8jvhnkast59drwdc"}}
```

Example nonzero error (no implied terminal state):

```json
{"schema_version":1,"error":{"code":"writer_active","message":"settlement intent recorded for run 01m42przrf8jvhnkast59drwdc; writer lease still held; retry with the same operation key","run_id":"01m42przrf8jvhnkast59drwdc","phase":"intent-recorded","retryable":true}}
```

Other stable errors: `settlement_conflict` (different intent/key), `writer_fence_unavailable` (missing/replaced lock, unsafe filesystem/path), `writer_uncertain` (unverifiable child/history/lock), `history_unavailable` (teardown postponed), `checkout_mismatch`, `merge_recovery_unverifiable`. Failure after an intent must disclose its persisted sequence and recovery command. A missing/unavailable daemon is **not** itself an error that authorizes cleanup: ask it to stop if reachable, otherwise wait on the inherited lease and verify history. Never use `caller.pi.exited`, PID disappearance, RPC EOF, or a same-UID API call alone as destructive authority.

## Crash/race proof obligations

| Boundary | Evidence and required result |
|---|---|
| Launch vs intent | Gate serializes both. Launch must acquire shared lease and complete `Start` (or prove failure) before releasing gate; settlement records intent under that same gate. No check-then-launch gap. |
| Daemon dies between generation reserve and Pi Start / response lost | Generation remains uncertain; inherited lease if child started. Reconcile exact identity, native file and ownership before any relaunch. Do not mint another generation from a timeout. |
| Pi exits while holding lease | Child and daemon share an open-file description; `LOCK_EX` cannot succeed until daemon releases after reap and any inheriting tools release. Pi exit fact alone never grants teardown. |
| Daemon/systemd `KillMode=mixed` restart | `Pdeathsig` acts on direct child; systemd may kill remaining service-cgroup processes after timeout. A detached tool or a child outside that cgroup may survive. Shared lease blocks while inherited; independent Taskfleet supervisor must be outside daemon cgroup. No cleanup by assuming a restart killed all writers. |
| Merge moved Git ref before report | Durable intent excludes new launches, transaction holds immutable OIDs. Reattached supervisor/retry acquires exclusive lease, verifies exact recorded integration and submits only the missing report; if unverifiable, preserve. |
| Supervisor dies after report / during teardown | Intent remains; new supervisor reacquires exclusive lease, checks recorded identities/history, converges cleanup or preserves work. No automatic fallback to workmux. |
| Lock pathname is replaced/unlinked while old FD held | `(dev,ino)` mismatch or missing path rejects new launch *and* settlement; do not create a fresh lock. Repair only with external audited reconciliation of all writers; same-UID malicious replacement cannot be made safe by flock alone. |
| History missing after Pi exit | Preserve checkout and binding; native history path/UUID must remain readable after teardown or be archived and verified before cleanup. Stopped Pi does not imply history retention. |

**Limit of the claim.** `flock` is advisory; a manual same-UID terminal Pi, editor, tool that dropped the FD, process writing through another path, or an adversary with write access to Taskfleet state can modify the checkout despite the lock. The daemon must refuse *managed* launches without the fence and warn that manual same-UID writers are outside the guarantee. Recheck Git cleanliness/identity immediately before each mutation; do not claim a cryptographic or kernel-enforced exclusive filesystem writer. If policy requires protection against arbitrary same-UID writers, it needs stronger OS isolation (distinct UID/mount namespace or equivalent), not an API attestation.

## Disposable Linux verification (implementation gate, not tests claimed here)

Use a temporary Unix home, `TASKFLEET_HOME` and Git repo under disk-backed `/var/tmp`; no live users, services, installed binaries or Pi history. A tiny compiled C/Go helper opens a 0600 file, `flock(LOCK_SH)`, forks+execs a child with an inherited FD, exits the parent, and has a second process attempt `flock(LOCK_EX|LOCK_NB)`: expect `EWOULDBLOCK` while child runs and success after it closes/exits. Repeat with child inheriting a detached tool, and with child not inheriting FD to show the limit. Add two concurrent launch/settle helpers at a barrier on the gate: exactly one ordering, and crash injection after intent append and after Pi `Start`; assert no second launch, stable inode and retry identity. Inject replace/unlink of the pathname while old FD is held; both sides must refuse, never create a second usable lock. Exercise recovery after ref movement and supervisor death with disposable Git state, including retained native JSONL unavailable.

If user systemd is available in an isolated disposable manager, create **two distinct** transient units/scopes: daemon fixture `KillMode=mixed` running a Pi-like direct child with `Pdeathsig=SIGKILL`, and Taskfleet-supervisor fixture outside its cgroup. Verify `/proc/<pid>/cgroup` differs before stopping daemon, then that Pi dies and supervisor survives; try an FD-inheriting descendant outside daemon cgroup and show it blocks settlement until stopped. If an isolated manager is unavailable, run only the FD/race fixtures and mark cgroup survival unverified; never start/stop the installed `native-agent-host-daemon@` unit. Existing Pi `piOwnership` under the runtime must be tested separately, not counted as this run fence.

**No product decision requested:** keep history after teardown and preserve work on uncertainty follow from the approved ownership split. Browser exposure of merge/cancel/discard remains the host's product choice; this protocol supplies the safe mechanics, not that UI decision.
