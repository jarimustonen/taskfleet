# Caller-owned writer fence (Taskfleet contract; host integration pending)

**Current Taskfleet settlement (source `main`):** Caller-owned single-node runs support `run merge <full-id> --node-id n-0001 --settlement-key KEY [--actor ACTOR] [--report-file JSON] --output json`, `run cancel <full-id> --settlement-key KEY --note REASON --output json` (whole run, no `--node`), `run salvage <full-id> --settlement-key KEY [--report-file JSON] --output json` (failed preserved run; no `--fence`), and `run discard <full-id> --force --reason REASON --settlement-key KEY --output json` (failed/cancelled retained work). Merge defaults to actor `caller-cli`; `--source` on merge/salvage may only repeat the recorded source. Cancel/discard require a reason; discard after cancellation reuses the cancel intent and key. `run settlement-intent <full-id> --node n-0001 --operation merge|cancel|discard --key KEY --actor ACTOR [--reason REASON] --output json` records intent and probes the lease but does not settle. These flags are in current source; an installed Taskfleet release may lag.

A real settlement records a sticky intent under the launch gate and requires the verified exclusive writer lease before Git mutation or terminal cancellation. `writer_active` returns `phase: intent-recorded`, the intent sequence and same-key recovery command without pretending a stopped Pi; a same-key retry may recover the linked OID-pinned merge transaction. Merge submits the explicit-merge report and returns `merged: true` with `cleanup: pending|complete`; supervisor recovery and Git-only teardown verify intent, immutable OIDs, retained Pi history and checkout identity under the lease. Cancel preserves work; discard needs an OID-pinned audit receipt and explicit force. A dry-run is read-only and cannot establish writer quiescence. Missing/replaced locks, unsafe checkout or unreadable history preserve work; there is no abandon command. None of these commands grants permission to launch Pi.

**Scope.** This is the Taskfleet ↔ Omega Habitat protocol for one caller-owned spinoff (`n-0001`), consistent with ADR 0010. Taskfleet creates persistent lock files and an identity ledger with the run; `run session fence` returns their identities with `launch_permission: false`. `run session reserve` records a gate/FD-checked Pi generation, and bind/update persist native history identity and lifecycle observations. The host has **not** implemented the gate-held daemon launch, FD inheritance into Pi, or browser integration. A standalone CLI response, including reserve or `caller.pi.lifecycle`, is not launch permission. Caller-owned creation, retry, merge and teardown never invoke workmux. The root issue remains open. This document refines [design.md](design.md), not its creation, placement or history rationale.

## Current FD boundary and pending host integration

Taskfleet stages `writer.lock` and `launch-gate.lock` as empty 0600 single-link regular files inside the 0700 staged run; `writer-fence.json` (0600) records their numeric `dev` and `ino`, and `run.created.data.writer_fence` repeats the identity. The files and ledger and their parent directory are synced before atomic publication; the published parent and staging parent are synced after rename. Keyed retry opens components from `/` with `openat(O_NOFOLLOW|O_CLOEXEC)`, validates the run directory owner and permissions, locks by the existing run `.lock` for reads, checks ledger against the creation event and reopens the directory/lock paths to compare identities. It does not replace missing state. A crash after creating lock files but before recording the identity in `run.created` can leave a private stage that must be preserved for manual investigation. A crash after the event is applied but before `node.created` reuses the recorded inode pair and finishes the node; an event fsynced without its first manifest projection still requires explicit log recovery. Never fabricate a new lock. Existing pre-fence caller runs remain readable but cannot be enrolled or settled by retry.

**Host dependency before any managed launch:** native-agent-host's `launchPiRPCSession` currently passes only `piOwnership` and workspace descriptors via `ExtraFiles`; it has no Taskfleet per-run descriptor and no gate-held admission. A standalone Taskfleet CLI cannot carry a flock over the host's `exec.Cmd.Start`: its exit releases the gate, leaving a check-then-start race with settlement. The host must implement a gate-held FD-aware integration: open the Taskfleet run directory from a trusted state root, verify exact run/node/checkout and recorded lock identities; take `launch-gate.lock` `LOCK_EX`, open `writer.lock` afresh and take `LOCK_SH|LOCK_NB`, invoke Taskfleet generation reservation with both FDs held, verify all parent/path/inode identities again, then supply that shared descriptor as an additional `ExtraFiles` entry to the Pi child. Keep both the gate and the daemon's own shared FD until `Start` returns or is proven to fail; release the gate only then. Keep the daemon shared reference until the direct child is reaped; inherited descendants may extend the lease. Never infer permission from `session bind`, `session update`, same UID, Pi exit or the returned create JSON. On lost Start response, treat that generation as uncertain and reconcile, not retry a new one. The reservation endpoint checks inherited FD identities and independently held locks; the host must keep the gate through Start because a same-UID CLI response is not ownership proof. The settlement side must serialize intent under the same gate and reject every missing/changed inode. Settlement requires the recorded fence; legacy pre-fence runs cannot be retrofitted on retry.

## Two locks, one durable intent

Use a **dedicated persistent per-run lock**, not the host's existing `piOwnership` lock. The latter is keyed by Pi session UUID under the daemon's ephemeral service runtime, and is recreated after reboot; a run can have several Pi generations/sessions. It excludes only cooperating writers of one native session, and Taskfleet cannot reliably find the same inode after a runtime restart. Keep that lock for native session ownership, but do not use it as Taskfleet's destructive-work fence.

At caller-owned creation, **Taskfleet** creates `<TASKFLEET_HOME>/runs/<full-id>/writer.lock` (initially under `.creating/<id>/`, atomically published with the run), and a separate `launch-gate.lock` there. Both are empty, permanent, regular 0600 files in 0700 same-UID directories on a local filesystem supporting Linux `flock`; include their `(st_dev, st_ino)` in the staged ledger and durable run creation record before publishing. Fsync files and parent directories, including after staging rename. Never unlink or replace either inode, including at teardown: retain the small run state as long as a bound session/history can be referenced. All participants open relative to a verified run-directory FD with `openat(..., O_NOFOLLOW|O_CLOEXEC)`, `fstat` UID=current mapped user, regular type, mode=0600, `st_nlink=1`, and match recorded device/inode; re-open/re-stat the pathname and its trusted parent before and after locking and before irreversible action. Reject symlinks, hard links, wrong owner/mode, inode change, unknown/missing metadata or unsupported flock filesystem as `writer_fence_unavailable`. Never create/repair missing locks on replay, reattach or settlement. Existing runs predating the ledger stay settlement-disabled until an explicitly reviewed recovery establishes safety; do not manufacture a replacement lock on demand. `TASKFLEET_HOME` itself must resolve to the verified same-user private state root; home/path changes are not silent migrations.

`writer.lock` is a **shared (`LOCK_SH`) lifetime lease** for each host Pi generation. The daemon obtains a fresh open-file description and nonblocking shared flock, verifies inode and run/node/checkout identity, and passes that FD through `exec.Cmd.ExtraFiles` into Pi **before** `Start`. Pi holds it through its entire lifetime, including daemon death; the daemon keeps its own reference until it has reaped that exact child, then closes it. Close-on-exec is cleared only for that explicit Pi child FD; avoid propagating it to tools unless those tools can still write to the checkout, in which case inheritance is deliberate and settlement waits for them too. The host's existing `Pdeathsig=SIGKILL` kills the direct Pi when the daemon dies but does not prove grandchildren or detached tools exited. Before releasing the daemon's FD, stop accepting RPC and account for direct child exit; inherited FDs from any participating descendants keep the lock held. Keep `piOwnership` for per-session exclusion in addition to, not instead of, this per-run lease. A daemon unable to pass/verify the FD must refuse launch, not launch unfenced Pi.

`launch-gate.lock` is a short-lived `LOCK_EX` mutex, **not** the lifetime lease. Every fresh launch and continuation for a bound caller-owned run must pass it. While holding the gate, acquire the run's exclusive `.lock`, replay unapplied events, verify the run/node/recorded checkout and that `settlement_intent` is absent and status is live; reserve the next generation with exact session identity in an append-and-apply event (`LockedRun`, fsynced event then projections). Still under the gate, open and take `LOCK_SH` on `writer.lock` (nonblocking), verify its inode again, then release the run lock, launch Pi with that inherited FD, and release the gate **only after Start has returned or been proven to fail**. Persist `caller.pi.started`/binding with their generation; a reserved generation with a lost launch response is *uncertain*, not an invitation to start another child. On restart first reconcile exact child ownership/lease/native history or record uncertainty and require intervention. An old session's continuation takes the same gate even if its native session lock is free. Browser requests and any alternate host entry point must use this path; refusal to acquire the gate is retryable, refusal due to intent is permanent for this run.

Taskfleet settlement first acquires the gate `LOCK_EX`, then the run `.lock` `LOCK_EX`, and appends an idempotent `caller.settlement_intent` event for `merge | cancel | discard` (full run/node ID, operation key, actor, reason as applicable, recorded lock dev/inode and generation). The event's durable presence, not an RPC stop receipt, closes admission: a launch holding the gate finishes acquiring its shared lease *before* intent can be recorded; a launch arriving afterward sees intent and cannot start. **No transient marker file or unchecked projection read may grant permission.** Drop run lock, then gate. The host should cease RPC/stop its Pi; Taskfleet takes `writer.lock` `LOCK_EX` with a bounded wait, and verify the *same inode* and checkout/Git identities again. A lock timeout means `writer_active` or `writer_uncertain`, preserving the intent and all work; it never means Pi has stopped. On uncertain lost response, read the intent under the run lock and resume the same operation key; different operations conflict. Intent is sticky even on merge conflict or timeout; there is currently no abandon operation.

**Lock order:** gate → run lock → shared lease for admission; gate → run lock (persist intent), release both → exclusive lease → Git merge lock → short run locks for transaction/report for settlement. Never block on the gate, lease or Git lock while holding the run lock. Supervisor and reattach acquire the exclusive lease *before* run lock for cleanup/recovery; they never acquire the gate while holding either. Dry-run uses shared-locked observations but cannot claim quiescence. Existing run/event APIs keep their exclusive `LockedRun` append witness, `applied_seq` replay and shared lock for multi-file reads. Git subprocesses are outside run-lock critical sections. Recheck intent and recorded inode under the run lock immediately before any destructive step; a path revalidation error preserves resources.

## Operation phases and outputs (protocol illustration; use current syntax above)

1. Host: `taskfleet run session reserve <id> --node n-0001 --generation 1 --pi-session-id <uuid> --checkout <absolute> --gate-fd <fd> --writer-fd <fd> --output json` is a *protocol operation*, not a standalone admission token: it runs with the daemon-held gate and shared lease FDs; the daemon must retain both through `Start`, since the CLI cannot do that for it. Taskfleet returns recorded run/checkout and generation; the daemon verifies exact repo, branch, canonical checkout, native history identity and same UID before spawning. A bare same-UID CLI assertion is never attestation of Pi ownership.
2. Operator: `taskfleet run merge <id> --node-id n-0001 --settlement-key <stable-key> [--report-file ...] --output json`. Phase `intent-recorded` may return `writer_active`, with no Git changes; the settlement producer holds the exclusive lease for Git transaction and report. Preserve the existing merge serialization, source-OID CAS and immutable-OID recovery; the Git-only driver may not call workmux. Successful `run merge` appends the `via: explicit-merge` report and confirms/reattaches an independent supervisor. **Never return cleanup complete merely because the report landed.** Cleanup may remain pending after the merge response; return `merged: true, cleanup: pending` with an exact reattach instruction.
3. Supervisor after report or restart: re-open the recorded inode, acquire exclusive lease (bounded/retry), read intent and immutable merge transaction under the run lock, verify retained Pi history is readable via its bound native ID/path (or a verified archive) and checkout/Git identities, then perform Git-only cleanup and record cleanup completion while holding the lease. Crash after Git ref move but before report: recovery must acquire exclusive lease and resolve only the recorded OIDs; until resolution it preserves the tree. An already recorded merge intent is sufficient to fence future launches even if the merge process dies and the lease is released. Reattach repeats the same check. Thus **logical quiescence lasts through cleanup** without depending on one process keeping `LOCK_EX` continuously: there is no interval for a *cooperating* new generation between the merger releasing its FD and the supervisor reacquiring it. Do not reopen launches after teardown.
4. Cancel while writer active: record `cancel` intent; the host should stop accepting RPC and request shutdown, but **defer terminal cancel/cleanup** until exclusive lease can be acquired; return `intent-recorded, writer_active` rather than `cancelled`. With lease held, append cancellation under the run lock; preserve branch and any dirty/unmerged checkout under existing non-merge rules. Do not equate cancellation with deletion or with permission for later Pi continuation. If the runtime is unavailable, this is still safely fenceable via local state but remains pending if a lease cannot be obtained.
5. `run discard --force --reason ...` is allowed only on failed/cancelled terminal runs with retained work. With the sticky intent and exclusive lease held, revalidate authorization, supervisor ownership, Git identities and history retention before audited `cleanup.discard_authorized`, then remove worktree/branch through Git; `--force` authorizes loss of work, **not** bypass of a writer lock, missing inode or unreadable history. `run salvage` uses the same merge path and intent, never the normal worker PID fence. Keep existing run/node/status rules and source relative work-preservation checks.

Illustrative success (not an exact output fixture):

```json
{"schema_version":1,"data":{"run_id":"01m42przrf8jvhnkast59drwdc","node_id":"n-0001","operation":"merge","phase":"reported","intent_seq":8,"writer_fence":{"state":"quiesced","lock_dev":2049,"lock_ino":53100},"merged":true,"cleanup":"pending","recovery_command":"taskfleet run reattach 01m42przrf8jvhnkast59drwdc"}}
```

Illustrative nonzero error (no implied terminal state):

```json
{"schema_version":1,"error":{"code":"writer_active","message":"settlement intent recorded for run 01m42przrf8jvhnkast59drwdc; writer lease still held; retry with the same operation key","run_id":"01m42przrf8jvhnkast59drwdc","phase":"intent-recorded","retryable":true}}
```

Other stable errors: `settlement_conflict` (different intent/key), `writer_fence_unavailable` (missing/replaced lock, unsafe filesystem/path), `writer_uncertain` (unverifiable child/history/lock), `history_unavailable` (teardown postponed), `checkout_mismatch`, `merge_recovery_unverifiable`. Failure after an intent must disclose its persisted sequence and recovery command. A missing/unavailable daemon is **not** itself an error that authorizes cleanup: ask it to stop if reachable, otherwise wait on the inherited lease and verify history. Never use `caller.pi.exited`, PID disappearance, RPC EOF, or a same-UID API call alone as destructive authority.

## Force-discard partial removal requiring manual recovery

A SIGKILL inside `git worktree remove --force` can leave a *registered* checkout whose `.git` file was removed. The same-key retry refuses it with `checkout_damaged` (or `checkout_mismatch` when the damage is otherwise unverifiable); it must not relax the checkout identity guard or claim automatic recovery. Preserve the run state, audit receipt, branch, and remaining checkout. Stop all writers, inspect `git worktree list --porcelain`, the recorded checkout/branch/OID and `cleanup.discard_authorized`, and back up remaining files. An operator can then repair the worktree's Git metadata using Git's worktree repair facilities if its identity is independently established, or reconcile/remove the damaged registration and checkout manually after verifying the receipt and retained history. Retry with the original key and reason only after restoring the recorded identity; if manual removal has already finished, verify both absence and the receipt independently. Do not prune or force-remove an unknown checkout on a guess. Safe automated repair is separate work.

## Crash/race proof obligations

| Boundary | Evidence and required result |
|---|---|
| Launch vs intent | Gate serializes both. Launch must acquire shared lease and complete `Start` (or prove failure) before releasing gate; settlement records intent under that same gate. No check-then-launch gap. |
| Daemon dies between generation reserve and Pi Start / response lost | Generation remains uncertain; inherited lease if child started. Reconcile exact identity, native file and ownership before any relaunch. Do not mint another generation from a timeout. |
| Pi exits while holding lease | Child and daemon share an open-file description; `LOCK_EX` cannot succeed until daemon releases after reap and any inheriting tools release. Pi exit fact alone never grants teardown. |
| Daemon/systemd `KillMode=mixed` restart | `Pdeathsig` acts on direct child; systemd may kill remaining service-cgroup processes after timeout. A detached tool or a child outside that cgroup may survive. Shared lease blocks while inherited; independent Taskfleet supervisor must be outside daemon cgroup. No cleanup by assuming a restart killed all writers. |
| Merge moved Git ref before report | Durable intent excludes new launches, transaction holds immutable OIDs. Reattached supervisor/retry acquires exclusive lease, verifies exact recorded integration and submits only the missing report; if unverifiable, preserve. |
| Supervisor dies after report / during teardown | Intent remains; new supervisor reacquires exclusive lease, checks recorded identities/history, converges cleanup or preserves work. No automatic fallback to workmux. |
| Lock pathname is replaced/unlinked while old FD held | `(dev,ino)` mismatch or missing path rejects new launch *and* settlement; do not create a fresh lock. Repair only with external audited reconciliation of all writers; same-UID malicious replacement cannot be made safe by flock alone. |
| History missing after Pi exit | Preserve checkout and binding; native history path/UUID must remain readable after teardown or be archived and verified before cleanup. Stopped Pi does not imply history retention. |

**Limit of the claim.** `flock` is advisory; a manual same-UID terminal Pi, editor, tool that dropped the FD, process writing through another path, or an adversary with write access to Taskfleet state can modify the checkout despite the lock. The daemon must refuse *managed* launches without the fence and warn that manual same-UID writers are outside the guarantee. Recheck Git cleanliness/identity immediately before each mutation; do not claim a cryptographic or kernel-enforced exclusive filesystem writer. If policy requires protection against arbitrary same-UID writers, it needs stronger OS isolation (distinct UID/mount namespace or equivalent), not an API attestation.

The disposable `crates/taskfleet/tests/fixtures/caller_writer_lease.c` helper demonstrates that a shared flock inherited by a fork/exec child survives its parent exit and blocks a separate exclusive probe until the child releases it. It does not test or implement host gate admission.

## Verification boundary

Taskfleet's disposable Rust/Git tests exercise fence identity, inherited-FD/lock behaviour, settlement retries, cancellation, discard receipts, ref-moved recovery and supervisor cleanup. These are not Omega Habitat daemon/Pi/browser end-to-end tests. The following external-host and systemd/cgroup tests have **not** been performed as part of this contract refresh; do not mistake the local release gate for them.

Use a temporary Unix home, `TASKFLEET_HOME` and Git repo under disk-backed `/var/tmp`; no live users, services, installed binaries or Pi history. A tiny compiled C/Go helper opens a 0600 file, `flock(LOCK_SH)`, forks+execs a child with an inherited FD, exits the parent, and has a second process attempt `flock(LOCK_EX|LOCK_NB)`: expect `EWOULDBLOCK` while child runs and success after it closes/exits. Repeat with child inheriting a detached tool, and with child not inheriting FD to show the limit. Add two concurrent launch/settle helpers at a barrier on the gate: exactly one ordering, and crash injection after intent append and after Pi `Start`; assert no second launch, stable inode and retry identity. Inject replace/unlink of the pathname while old FD is held; both sides must refuse, never create a second usable lock. Exercise recovery after ref movement and supervisor death with disposable Git state, including retained native JSONL unavailable.

If user systemd is available in an isolated disposable manager, create **two distinct** transient units/scopes: daemon fixture `KillMode=mixed` running a Pi-like direct child with `Pdeathsig=SIGKILL`, and Taskfleet-supervisor fixture outside its cgroup. Verify `/proc/<pid>/cgroup` differs before stopping daemon, then that Pi dies and supervisor survives; try an FD-inheriting descendant outside daemon cgroup and show it blocks settlement until stopped. If an isolated manager is unavailable, run only the FD/race fixtures and mark cgroup survival unverified; never start/stop the installed `native-agent-host-daemon@` unit. Existing Pi `piOwnership` under the runtime must be tested separately, not counted as this run fence.

**No product decision requested:** keep history after teardown and preserve work on uncertainty follow from the approved ownership split. Browser exposure of merge/cancel/discard remains the host's product choice; this protocol supplies the safe mechanics, not that UI decision.

## Settlement-intent probe and shipped settlement

`run settlement-intent <full-run-id> --node n-0001 --operation merge|cancel|discard --key KEY --actor ACTOR [--reason REASON] --output json` records exactly one sticky `caller.settlement_intent` with full identities, current generation, lock dev/ino, audit fields and event sequence. Cancel/discard require a reason. The gate serializes this write against a cooperating launch which holds the gate through Start; the run lock protects the append/replay. An identical retry returns the same sequence after a lost reply; a different payload conflicts. It then releases gate and run lock before a bounded nonblocking writer-exclusive lease probe. `writer_active` includes phase `intent-recorded`, the persisted intent and a retry command in the error details. `quiesced` is only an observation: the command releases its FD before returning and **never performs or authorizes Git or cleanup**. `run show --output json` exposes `manifest.caller_settlement_intent`. New reservations and bindings are denied after intent, while an existing generation's exit/failure/uncertainty reconciliation can still be recorded. No abandon command exists; the intent survives all failures. Merge, cancel, salvage, discard and supervisor recovery/teardown have fenced paths; the probe itself performs none of them.

**Shipped producer and supervisor:** `run merge` and caller salvage invoke the fenced Rust Git-only producer; it holds the exclusive writer FD across the OID-pinned driver and terminal report. `merge.started` links intent sequence/key/writer inode. Supervisor recovery verifies the linked immutable transaction under the lease, and supervisor teardown verifies the native history and Git identities before clean worktree/branch removal. A failed driver retains intent and work; ref-moved crashes are recoverable only when those immutable facts can be proved. Caller cancellation records terminal status only after the lease is held and retains the checkout. Force discard is an operator action, not supervisor deletion. No caller path uses workmux/tmux. An advisory flock cannot fence uncooperative same-UID writers; intent or an unlocked lease probe is never a transferable authorization token.
